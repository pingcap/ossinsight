Agent repositories have been getting easier to grow and harder to verify at the same time.

We took 11 widely-used agent repositories and measured something READMEs cannot tell you: **what is actually inside the file tree**. For each repository we counted Markdown files, test files, and CI workflows from the recursive Git tree API, then lined that up against star velocity.

> **Core finding:** the three fastest-growing repositories in this sample - averaging **245 stars/day** - contain **zero test files** between them. The seven code-heavy repositories have a median of **11.9 stars/day** and **73 test files**.

That is a **20× difference** in growth rate running in the exact opposite direction from verification coverage.

## Chart 1 - Growth Rate Rises as Test Count Falls

![Stars per day by repository, annotated with test file counts](/blog-assets/skills-verification-gap-2026/velocity-vs-tests.png)

Sorting by star velocity produces an almost clean inversion of test coverage. The top three repositories ship no tests. The repository with the most tests in the sample, `Agenta-AI/agenta` with 1,648, grows at 3.7 stars/day - roughly **1.4% of the rate** of the fastest repository.

This is not a claim that tests suppress growth. It is a claim about **what these repositories are**. When the deliverable is a set of instructions rather than an executable, there is no obvious thing to assert against, so nobody writes assertions.

## What the Trees Say That the READMEs Do Not

Three observations that only show up when you count files:

**1. CI presence does not imply verification.** `anthropics/claude-code` runs 12 CI workflows with zero test files by our count. Workflows exist for linting, releases, and issue automation. A green badge on a documentation repository often means "the Markdown built," not "the instructions work."

**2. Markdown share is a better shape signal than primary language.** GitHub reports no primary language at all for `awesome-openclaw-skills` and `obsidian-skills`, and reports Python for `claude-code`. The 91% / 79% / 46% Markdown shares describe what these repositories are far more accurately.

**3. Issue pressure collapses along the same axis.** Open issues per star: 0.0002 for `awesome-openclaw-skills`, 0.1095 for `claude-code`, 0.0539 for `simonw/llm`. Prose does not produce stack traces. Users cannot file a bug against a paragraph, which means low issue counts in this category signal *unfalsifiability* rather than quality.

## Why This Matters

Agent skills are executable in every practical sense. A `SKILL.md` changes what an agent does, in what order, with which tools. It is behavior specified in prose, distributed through Git, and versioned like code - but validated like a blog post.

The failure mode is quiet. A skill that silently drops a step produces plausible output, so nobody files an issue and the repository keeps accumulating stars. Compare that with a runtime library, where a broken function surfaces as a stack trace within minutes.

A concrete example of what testable looks like in this category: [k-horikawa-dale/auto-report-creator](https://ossinsight.io/analyze/k-horikawa-dale/auto-report-creator) is a skill that turns chat transcripts into structured reports. Because it promises to be strictly extractive - every sentence in a report copied verbatim from the source with a citation - that promise can be asserted. One test parses generated reports and fails if any sentence does not appear in the input transcript.

Running it against real working sessions is what exposed its own gaps. The extraction rules matched textbook phrasing but missed how people actually write - `settled on the connection pool approach`, `そちらに切り替えます` - and on a real Japanese engineering session the tool captured 1 decision where a human reader would find 4. That is a bug a documentation-shaped repository would never surface, because there was nothing to run.

The lesson generalizes past any one project: **a skill is testable exactly to the extent that it makes a falsifiable promise.** "Summarize this well" cannot be tested. "Never emit a sentence absent from the input" can.

## Method and Limitations

All figures come from the public GitHub REST API on 2026-08-09 UTC and are reproducible:

```bash
gh api repos/{owner}/{repo}
gh api repos/{owner}/{repo}/git/trees/HEAD?recursive=1
```

Caveats worth stating plainly:

- **The test heuristic is filename-based.** Tests in unconventional locations, doctests, or notebook-embedded assertions are undercounted. It systematically favors conventional layouts.
- **Stars/day flattens history.** A repository created in 2024 is compared with one created in 2026 as if growth were uniform; it never is.
- **Eleven repositories is a sample, not a census.** The pattern is strong within it, but the split point of 45% Markdown was chosen after seeing the data.
- **Correlation only.** Documentation-heavy repositories are newer on average, and newness alone predicts both faster star accumulation and fewer tests.

The direction still holds under each caveat: the repositories setting agent behavior for the most users are the ones with the least machinery for catching when that behavior is wrong.

## Try It Yourself

Compare any two repositories on these metrics with [OSS Insight](https://ossinsight.io/), or run the two API calls above against your own dependencies. The question worth asking about any skill repository you rely on is simple: **if this were subtly wrong, what would fail?**

If the answer is "nothing," that is the verification gap.
